# Caching layers

> [Назад к оглавлению](../../README.md)

Запрос в приложении на synapse может быть отвечен из **трёх независимых слоёв**, стоящих друг над
другом. Это не конкурирующие стратегии — каждый слой решает свою задачу, знает разное и включается
независимо. Эта страница объясняет весь стек один раз, чтобы остальные доки
([ApiClient](./api-client.md), [WorkerCacheStorage](./worker-cache-storage.md), рецепты
[ServiceWorker](./custom-fetch-service-worker.md) и [fetchFn](./custom-fetch-fn.md)) могли
сосредоточиться каждая на своём слое.

```
ваш компонент / эффект
        │
        ▼
┌───────────────────────────────────────────────┐
│ 1. КЭШ ПРИЛОЖЕНИЯ — ApiClient + storage       │  знает ВАШ домен: эндпоинты, теги, ttl
│    (Memory / LocalStorage / IndexedDB /       │  хит ⇒ fetch() вообще не вызывается,
│     WorkerCacheStorage)                       │  строки в Network нет
└───────────────────────────────────────────────┘
        │ кэш-промах → клиент вызывает fetch()
        ▼
┌───────────────────────────────────────────────┐
│ 2. ТРАНСПОРТ — baseQuery.fetchFn              │  КАК выполняется запрос
│    (auth-retry, метрики, axios, worker)       │  не кэш — шов между слоями
└───────────────────────────────────────────────┘
        │
        ▼
┌───────────────────────────────────────────────┐
│ 3. СЕТЕВОЙ СЛОЙ — ваш ServiceWorker           │  знает URL и HTTP: офлайн, precache,
│    + Cache API (ниже — HTTP-кэш браузера)     │  стратегии; строка "(ServiceWorker)"
└───────────────────────────────────────────────┘
        │
        ▼
      сеть
```

## The request path

Что реально происходит, когда хук или эндпоинт запускает запрос:

1. **`ApiClient` проверяет свой кэш** в `storage` (по ключу кэша, ttl, тегам). При валидном хите
   ответ отдаётся из хранилища — `fetch()` **не вызывается вовсе**, слои 2–3 запрос не видят, а в
   DevTools → Network **нет строки вообще**.
2. При промахе клиент выполняет запрос через **транспорт** — встроенный `fetch` или ваш
   `baseQuery.fetchFn`, если вы его передали.
3. Именно этот вызов `fetch()` может перехватить **ServiceWorker**: ответить из своего Cache API,
   сходить в сеть или синтезировать офлайн-фолбэк. Ниже него — обычный HTTP-кэш браузера.
4. Ответ поднимается обратно: SW возвращает его в `fetch`, клиент кладёт его в кэш приложения (если
   кэширование включено для этого эндпоинта) и резолвит ваш запрос.

Два следствия, которые стоит усвоить:

- Слои **затеняют** друг друга сверху вниз: хит на слое 1 означает, что нижние слои не делают ничего.
- Инвалидация живёт **послойно**: `invalidatesTags` чистит только слой 1; SW-кэш живёт по своей
  стратегии (stale-while-revalidate и т.п.) и ничего не знает о ваших тегах.

## Layer 1 — application cache (storage)

Это собственный кэш `ApiClient`, живущий в том storage, который вы ему дали. Он хранит
**распарсенные данные** и понимает **семантику вашего API** — поэтому умеет то, что не может ни один
нижний слой:

- **Инвалидация по тегам** — мутация с `invalidatesTags: ['notes']` сбрасывает все закэшированные
  запросы с тегом `notes` и авто-рефетчит активные. SW так не может: он видит непрозрачные URL→байты.
- **Реактивность** — хуки перерисовываются от обновлений кэша и подписок.
- **Синхронный fast-path** — на sync-хранилищах (`MemoryStorage`, `LocalStorage`) закэшированный
  результат читается синхронно уже на первом рендере (без вспышки loading), что важно для
  SSR-гидрации.
- **Кэширование — opt-in и только GET** — без конфига `cache` ничего не кэшируется; мутации не
  кэшируются никогда.

Выбранный storage определяет *область видимости и время жизни* кэша:

| Storage | Область | Переживает перезагрузку | Sync fast-path |
|---|---|---|---|
| `MemoryStorage` | одна вкладка | нет | да |
| `LocalStorage` | по вкладке, данные общие через диск | да | да |
| `IndexedDBStorage` | по вкладке, данные общие через диск | да | нет |
| `WorkerCacheStorage` | **живой, все вкладки сразу** | пока жива хоть одна вкладка | нет |

`WorkerCacheStorage` — это по-прежнему слой 1: он лишь переносит `Map` кэша в SharedWorker, и все
вкладки делят один живой кэш (одна вкладка сходила в сеть — у всех кэш-хит).

## Layer 2 — transport (baseQuery.fetchFn)

Не кэш — **шов** между слоями: заменяет то, *как* клиент выполняет запрос после промаха слоя 1.
Auth-retry, метрики/трассировка, инстанс axios, `postMessage`-мост в Worker. Слой 1 работает поверх
без изменений, а то, что транспорт в итоге `fetch`-ит, по-прежнему перехватываемо слоем 3. См. рецепт
[Кастомный `baseQuery.fetchFn`](./custom-fetch-fn.md).

## Layer 3 — network (your ServiceWorker + Cache API)

Собственный `sw.js` приложения, регистрируемый рядом с библиотекой (не внутри неё). Он перехватывает
платформенный `fetch` и реализует **сетевую политику**: precache шелла, офлайн-фолбэки, стратегии по
URL (cache-first / network-first / stale-while-revalidate). Он знает URL и HTTP — не ваши эндпоинты
и теги — и покрывает в том числе запросы, которые делал не ваш код (картинки, шрифты). Поскольку он
сидит ниже `fetch`, каждый его ответ виден в Network строкой с пометкой `(ServiceWorker)`. См. рецепт
[Собственный fetch-перехватывающий ServiceWorker](./custom-fetch-service-worker.md).

Ниже SW есть и четвёртый, бесплатный слой, которым вы не управляете: HTTP-кэш браузера (заголовки
`Cache-Control` → строки `(from disk cache)`).

## Other libraries do the same

Такое разделение — стандартная архитектура веба, а не изобретение synapse. TanStack Query, SWR,
RTK Query и Apollo держат собственный кэш уровня приложения, и никто из них не делегирует его
ServiceWorker'у; Workbox существует ровно как инструмент слоя 3, и типичный PWA-стек — это кэш
приложения **плюс** Workbox бок о бок. Браузер добавляет HTTP-кэш под ними всеми. Слоистое
кэширование с разным знанием на каждом слое — норма.

## Choosing a setup

- **Data-driven SPA (по умолчанию)** — только слой 1: конфиг `cache` + теги на `ApiClient`. Без SW.
- **То же, но общее между вкладками** — слой 1 с `WorkerCacheStorage` в роли storage клиента.
- **PWA / офлайн** — слой 1 для семантики данных **плюс** свой SW (слой 3) для офлайна и precache.
  Слои не конфликтуют: хит слоя 1 просто никогда не доходит до SW.
- **«Кэшировать только в ServiceWorker»** — полностью валидно: не включайте кэш `ApiClient` (он
  opt-in) и отдайте кэширование своему SW. Останутся типизация эндпоинтов и состояние запросов, но
  вы отказываетесь от инвалидации по тегам, авто-рефетча после мутаций и синхронного fast-path —
  каждый хит будет полным round-trip'ом `fetch` через SW.
- **Auth / метрики / кастомный транспорт** — слой 2 (`fetchFn`), ортогонален всему вышеперечисленному.

## DevTools Network cheat-sheet

Вкладка Network говорит, какой слой ответил:

| Что вы видите | Кто ответил |
|---|---|
| строки нет вообще | слой 1 — кэш приложения (в т.ч. `WorkerCacheStorage`) |
| строка с пометкой `(ServiceWorker)` | слой 3 — ваш SW (из его Cache API или сети) |
| строка `(from disk cache)` / `(memory cache)` | HTTP-кэш браузера |
| обычная строка с таймингом | настоящая сеть |
