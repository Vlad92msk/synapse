# Аудит: слайс-на-сущность («synapse family») вместо keyed-кэша внутри одного стора

> **Это АУДИТ, а не задача на реализацию.** Нужен разбор идеи с вердиктом, а не код.
> Ответы обосновывай ФАКТАМИ из исходников `packages/synapse/src` (ссылки `file:line`), а не
> общими словами. Где идею подтверждает/опровергает прайор-арт — назови конкретную библиотеку и её
> механизм. Финал — явная рекомендация: делать / не делать / делать частично, с обоснованием.

---

## Идея, которую надо оценить

Сейчас модуль, обслуживающий данные для МНОЖЕСТВА сущностей, держит их как keyed-кэш внутри
одного стора: `Record<key, …>` (в проекте-потребителе — comments: `byTarget['post:123']`,
`byTarget['media:456']`, плюс параллельные `countByTarget`/`cursorByTarget`/… по тем же ключам).

**Гипотеза:** вместо ключей — создавать ОТДЕЛЬНЫЙ инстанс слайса synapse на каждую сущность
(«family» модулей, параметризованных ключом). Один тред = один инстанс со своим state/dispatcher/
selectors/effects. Предполагаемые выгоды автора идеи: проще DX, больше гибкости, вероятно —
оптимизация (изоляция, отсутствие проблемы гидрации-затирания, естественный GC по ключу).

Это по сути паттерн **atomFamily / query-family**. Аудит должен сказать, оправдан ли он для
synapse и что для него уже есть/чего нет.

---

## Откуда идея (контекст)

Keyed-кэш в одном сторе породил конкретную боль в SSR-гидрации: библиотечный `hydrate` работает
по верхнеуровневым ключам, а target-ключи лежат на втором уровне (`byTarget[key]`), поэтому
серверный снапшот при full-replace/top-level-merge затирал живые клиентские срезы. Пришлось
держать ручной двухуровневый мердж в потребителе (`FeedCommentsSeed`/`seedFromServer`). Deep-merge
в либе сознательно отвергнут как переусложнение (см. `tasks/toTanstack/SSR_HYDRATION_AUDIT_TODO.md`,
пункт 7). Если каждая сущность — отдельный слайс, проблема гидрации-затирания исчезает by
construction (каждый слайс гидрируется своим снапшотом независимо). Это и есть повод для аудита.

## Прайор-арт — с чем сравнивать (обязательно свериться)

- **Jotai `atomFamily` / Recoil `atomFamily`** — параметризованные атомы: инстанс на ключ, ленивое
  создание, ручной/GC-сброс. Ближайший аналог «слайс-на-сущность». Изучить их API управления
  жизненным циклом (создание/удаление/утечки).
- **TanStack Query** — кэш ПЛОСКИЙ по `queryKey`: фактически «запись на ключ», но не отдельный
  стор-инстанс, а записи в одном кэше. Это середина между keyed-в-одном-сторе и слайс-на-сущность.
- **Redux Toolkit `createEntityAdapter`** — контр-аргумент: нормализованный keyed-кэш в ОДНОМ
  слайсе намеренно. Почему RTK не идёт в «слайс на сущность»? (масштабируемость, DevTools, единый
  reducer). Учесть эти доводы.
- **Zustand** — обычно один стор; динамические сторы возможны, но управляются вручную.

Вывод по прайор-арту: паттерн существует (Jotai/Recoil), но мейнстрим управления серверными данными
(TanStack/RTK) держит ПЛОСКИЙ keyed-кэш, а не инстанс-на-ключ. Аудит должен объяснить, к какому
лагерю ближе synapse и почему.

## Что выяснить по КОДУ synapse (главное)

- [ ] **Поддерживает ли synapse сегодня динамическую family?** Есть ли фабрика, которая лениво
      создаёт + кэширует + утилизирует инстансы модуля по рантайм-ключу, или модуль синглтон by
      construction? Проверить `createSynapse`, `createSynapseCtx` (клиентский main-синглтон,
      `getClientStore`), `fork()`, `dehydrateModule`, реестр модулей/awaiter. Ссылки на код.
- [ ] **Жизненный цикл инстанса.** Создание, монтирование провайдера, destroy/cleanup, GC при
      отсутствии наблюдателей. Что уже есть (`destroy`, `cleanupSynapse`), чего нет для «многих
      короткоживущих инстансов». Утечки RxJS-подписок.
- [ ] **Стоимость эффектов на инстанс.** Каждый слайс поднимает свой RxJS-пайплайн/эффекты/
      зависимости. Во что обходятся N одновременно живых инстансов vs один стор с keyed-логикой?
      Есть ли шаринг зависимостей (`dependencies: [coreSynapse]`) между инстансами family?
- [ ] **Провайдер-модель React.** `createSynapseCtx` даёт один контекст на модуль. Как выглядит
      «провайдер на ключ»? Нужен ли `<Family>`-контейнер / хук `useEntitySynapse(key)`? Что это
      значит для дерева провайдеров (у comments сейчас вложенность posts/comments/reactions).
- [ ] **SSR/гидрация family.** Дегидрация ДИНАМИЧЕСКОГО набора инстансов (сколько тредов на
      странице) и их засев. Пересекается с пунктом 4 TODO (карта снапшотов на мульти-модуль) —
      оценить, решает ли family эту задачу заодно.
- [ ] **Кросс-слайс агрегаты.** Что ломается, когда данные разнесены по инстансам: общий счётчик,
      LRU-вытеснение «холодных» тредов (сейчас `MAX_CACHED_TARGETS`), observers, батч-запросы
      счётчиков (`loadCounters`), realtime-подписки. Кто управляет капом/эвикшеном над family?
- [ ] **DX по факту.** Стало ли ПРОЩЕ, или сложность переехала из keyed-логики стора в менеджер
      жизненного цикла family? Сравнить на реальном примере comments: «как пишется тред-компонент
      сейчас» vs «как писался бы с family».
- [ ] **DevTools/отладка/типы.** Наблюдаемость N инстансов, типизация параметризованного модуля.
