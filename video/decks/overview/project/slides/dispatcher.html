Бизнес-логика · диспетчер

import { Dispatcher } from 'synapse-storage/reactive'

export class PokemonDispatcher extends Dispatcher<PokemonState> {

readonly selectPokemon = this.action((store, id: number | null) => {

store.update((s) => { s.selectedPokemonId = id })

return id                                   // payload → эффектам

})

readonly setSearchQuery = this.action(

(store, query: string) => { store.set('searchQuery', query); return query },

{ memoize: (cur, prev) => cur === prev },   // тот же аргумент — пропуск

)

readonly loadMore = this.signal<void>('Подгрузить следующую страницу')

readonly loadDetails = this.apiActions<void>((s) => s.api.detailsRequest)

// d.loadDetails() — намерение · .loading() · .success() · .failure(msg)

readonly watchFavoriteCount = this.watcher({ selector: (s) => s.favorites.length })

}

стор

action$ → эффекты

Диспетчер — это список всего, что модуль умеет делать. В одном классе. Импортируем Dispatcher и наследуемся от него, указав тип состояния. Первый вид — action. Это экшен, который сам меняет состояние. Он получает хранилище и параметр. То, что он вернёт, станет payload: его увидят эффекты. У action есть опции. memoize пропускает повторный вызов с тем же аргументом. Ещё можно передать meta — произвольное описание. Второй вид — signal. Он ничего не меняет. Это чистое намерение, например „подгрузить следующую страницу“. Что именно делать — решат эффекты. Третий — apiActions. Это готовая группа статусов запроса. Вызов группы — это намерение загрузить. А loading, success и failure пишут статус в ячейку состояния, на которую вы указали. И четвёртый — watcher: поток изменений части состояния. Имя поля — это имя экшена. Компонент вызывает selectPokemon и не знает, что произойдёт дальше. Читаем селекторами, пишем диспетчером.
